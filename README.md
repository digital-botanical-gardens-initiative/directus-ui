# DBGI sample explorer

A small, read-only dashboard for DBGI **Field_Data** and its linked **Taxa** hierarchy: sample search, resolved Catalogue of Life (CoL) names, family queries, list/map exploration, garden progress, a collectors leaderboard, a taxonomic treemap, and individual field records with embedded OpenStreetMap locations and historical weather estimates. **Directus is the sole source of collection and processing records.** This dashboard does not replace collection protocols, deposit workflows, complete mass-spectrometry lineage, spectra, or staff tools. Counts are field records; distinct resolved taxa are CoL usages, not necessarily species.

## Why a snapshot?

Directus at `https://emi-collection.unifr.ch/directus` does not send `Access-Control-Allow-Origin` to GitHub Pages, so the browser cannot read the API directly. `Field_Data` is anonymously readable, but `Taxa` returns HTTP 403 to anonymous requests. `scripts/build_snapshot.py` reads both collections server-side using a **read-only Directus token**, or a local login file, validates pagination and ancestry, and atomically writes `data/samples.json`. The browser reads that same-origin JSON; **no credentials, `.env`, or Python runtime are shipped to visitors**.

The main sample export includes only Field_Data record/sample ID, project, unified field name (falling back to `taxon_name` or `sample_name`), collection date, GeoJSON point, Taxa relation ID, and resolution status; Taxa export includes CoL ID, scientific name, authorship, rank, parent ID and backbone version. Collector identity is kept in a separate, explicitly published leaderboard snapshot; photos, comments, and other fields are omitted. The scientific name shown as **resolved** comes exclusively from `Taxa.scientific_name` through `Field_Data.taxon_ref`; a field name never silently substitutes for an unresolved name. `Taxa.parent_ref` supplies the full ancestry. A family filter includes every sample whose resolved taxon is that family or a descendant of it (e.g. Rubiaceae), not text matches on a field name. Missing links stay unresolved. GeoJSON coordinates are `[longitude, latitude]`; source fields named `latitude`/`longitude` appear reversed in observed records and are not used. Review coordinate sharing and public release of the restricted Taxa projection and collector names before publishing these snapshots.

## Run and refresh locally

Requires Python 3.10+ for the exporter; the site itself uses plain HTML/CSS/JavaScript.

```sh
python3 scripts/build_snapshot.py --env-file ../directus-explorer/.env.admin
python3 scripts/build_collectors.py --env-file ../directus-explorer/.env.admin
python3 scripts/build_garden_progress.py --env-file ../directus-explorer/.env.admin
python3 scripts/build_ms_profile.py
python3 scripts/build_processing.py
python3 -m http.server 8000
```

The local admin file already exists in the neighboring repository; it is used only to fetch the snapshots and is **never copied** into the site. Prefer a read-only token for regular refreshes: set `DIRECTUS_TOKEN` in the environment and run the exporters. That token needs `Field_Data`, `Taxa`, and `People` **read** access for sample/taxonomy and collector refreshes, including their projected fields and aggregates. `DIRECTUS_INSTANCE` optionally overrides the API URL. Open `http://localhost:8000/`; do not use `file://` because browsers block local JSON fetches. The checked-in snapshots work without any credentials until their next refresh.

Use the home-page search or **Samples** to find sample IDs, field names or resolved CoL names; type all or part of a **CoL family** name (e.g. `Rubiaceae` or `Rubi`) in the family search box. Suggestions come from families with linked samples. Family matches include descendants in the CoL hierarchy, not text matches on field names. Combine it with the garden/project and sample search filters, then switch between **List** and **Map** without losing the selection. Nearby points are grouped into numbered bubbles at zoom levels below 19 for readability; **each click on an aggregate moves just one zoom level closer to that group**, so you can continue drilling down progressively. At the deepest zoom (19), **each sample has its own clickable purple point without a border or shadow**; coincident sample icons fan apart only for display, with thin lines back to their **identical, exact recorded position** and raw coordinates in each popup. No spatial average replaces source coordinates at maximum zoom. Records without coordinates remain available in the list and are counted above the map. **Explore → Families** shows 20 families per page with horizontal count bars, Previous/Next and direct drilldown; **Most collected CoL taxa** groups by Taxa primary key. Sample pages show the original project and, for garden records, the garden name, with the unified field name **separately** from the resolved scientific name, rank, CoL ID, family and expandable full classification.
The **Families** and **Most collected CoL taxa** tables use the same aligned horizontal bars and numeric counts. Each table scales its bars to its own most-collected row: family bars count all descendant field samples, while the CoL taxon bars count only field samples linked to that exact Taxa primary key.
The **Samples** list shows separate evidence badges for the field collection, a linked extraction record, and a recorded MS file **for that exact Field_Data sample**. “Extraction recorded” includes records whose status is not OK and does not assert successful extraction; its recorded statuses appear on hover and in the processing panel. “MS file recorded” requires that sample's linked `MS_Data` file with status OK/published, not merely another sample of the same species. If either optional processing snapshot is unavailable, its badge says unknown, not “no record”.

Use **Profiled samples only** to keep field samples with their own OK/published Directus `MS_Data` file; it combines with project, CoL family, sample search, and both List and Map. A different sample of the same species having an MS file is not enough. If the MS snapshot cannot load, this control stays disabled rather than reporting an incorrect unprofiled result. **Clear filters** removes this selection too.

Use **Order by** in the main Samples view to sort the full matching snapshot by sample ID, resolved name, field name, family, project, collection date or recorded MS file before the 40-row pages are cut. Search also matches family, project, garden and recorded date; CoL family, project and **Profiled samples only** remain independent filters. In **Explore**, the family table filters by typed name and sorts by name, sample count or distinct taxa **before pagination**. The garden-progress, project and Most collected CoL taxa tables offer field-based filter/order controls over their displayed rows (the Most collected table remains the **top 20**, not a search across all taxa). All these operations are local on the Directus-derived snapshot.

The sample map loads pinned Leaflet 1.9.4 CSS/JS from unpkg **only when Map is selected**, with Subresource Integrity; base-map tiles come from OpenStreetMap with attribution. Sample detail maps use a lazy OpenStreetMap iframe. These maps need network access and expose visitors' requests to those third parties; the sample list, family search and treemap work without them. Snapshot timestamp and source count appear on the overview. Search and grouping run locally on static JSON; no live browser-to-Directus calls occur.

Each sample row links to its exact Directus `Field_Data` item. On the sample page, the **Directus record ID** itself links to the field record and the **Taxa Directus ID** links to its resolved taxon for curators who can access the admin UI; the separate CoL usage ID is not a Directus item ID. Taxonomic classification, family rows and treemap details link instead to public [Catalogue of Life taxon pages](https://www.catalogueoflife.org/data/search) using the linked Taxa record's CoL ID (`/data/taxon/<CoL ID>`). The public site may show a newer backbone than the snapshot and can limit automated access. The UI italicizes genus names and species/infraspecific epithets, but not rank markers or authorship. Garden/project aggregates are not Directus items, so they link to filtered samples rather than fabricated item URLs.
The sample page links botanical gardens to their filtered dashboard map, projects to their filtered sample list, and CoL families to the descendant-inclusive family search and public CoL pages. Resolved species names link to the species dashboard, CoL usage IDs and ranks to public CoL records, and the recorded field name and record ID to their Field_Data source. Unresolved names and missing fields never receive an invented CoL or species link.

## Species and specimen processing

Select a resolved species in the **Samples** list or follow **All field samples of …** on a sample page to open `#species/<Taxa ID>`. Its paginated field-sample cards include identifications at species or descendant ranks according **only** to the Directus Taxa parent hierarchy. The species-level MS indicator reports how many *field samples* have linked MS files and which instruments were used; open an individual field sample for its own dried material, extracts, aliquots, MS records and GNPS file. A species-level MS badge is not evidence that every listed sample was profiled.

For a genus, family, order, or other non-species rank, follow its **Related samples** link in a field record's classification, a **Family page** link in the family table, a **Taxon page** link in the taxonomy table, or a treemap taxon link. `#taxon/2984` (*Quercus*) lists every linked field sample identified as that genus **or any descendant**, including species/infraspecific identifications; cards are paginated and the **Map** plots every geolocated match. The map groups points until the deepest zoom, where individual samples are clickable. All membership and classification come only from `Field_Data.taxon_ref` and parent links in the Directus `Taxa` snapshot; field-name spelling, the Portal and CoL website are not used to assign samples.

Upper-taxon pages such as `#taxon/2089` (*Passiflora*) offer **Cards**, **Map** and a compact **List** with the same sample set. Search within the current taxon, choose garden/project and identification rank, optionally restrict to this sample's own MS file, and order by sample ID, resolved name, field name, family, project or collection date; controls apply to the **whole matched set before paging** and also restrict the map. The MS-only option stays disabled if its Directus snapshot cannot be read. The classification breadcrumb links to the corresponding ancestor pages.

Species and upper-taxon pages show their **Directus Taxa ancestry** as dashboard links and offer the matching public Catalogue of Life page using its recorded CoL ID (e.g. `#species/539` → [CoL 3VCC8](https://www.catalogueoflife.org/data/taxon/3VCC8)). CoL's anti-bot challenge loops or rejects embedded frames, so the dashboard links to the official page rather than embedding it. The dashboard does not proxy, copy, or replace that CoL page, and the Directus lineage remains available even if CoL is offline.

Species pages optionally display a gallery of **iNaturalist taxon reference photos**, separate from the **Curation_Data observation photos on individual sample pages**. The dashboard starts with that species' exact Directus CoL ID and the checked-in CoL→Wikidata QID match; when this panel enters view, it queries that Wikidata item's [iNaturalist taxon ID (P3151)](https://www.wikidata.org/wiki/Property:P3151), then requests the iNaturalist species-taxon API. Only a **single linked, active species taxon** and its individually credited CC-licensed photos are shown. Ambiguous, unlinked or inactive taxa never receive guessed photos, and unlicensed photo URLs are omitted. The external iNaturalist name can differ from the recorded CoL name; neither pictures nor iNaturalist classifications are used for Directus sample grouping. For example `#species/1077` (*Ruscus aculeatus*) links via Wikidata `Q161425` to iNaturalist taxon `82904`. The supplied *Citrus deliciosa* taxon `765426` is **not** a match to any sampled Directus species of that name; the dashboard does not assign its pictures to a different citrus.

The lazy gallery sends the visitor's IP and **species Wikidata QID** to Wikimedia, and IP and **iNaturalist taxon ID** to iNaturalist; displayed photo requests reach iNaturalist's image host. It sends no Directus sample ID or location, suppresses referrers, stores no external photos in this repository and retains a link/attribution for each image. An unavailable public API affects only this optional gallery.

When a field sample has linked `Dried_Samples_Data`, `Extraction_Data`, `Aliquoting_Data` or `MS_Data` records, its **Specimen processing** panel links those records and their `Containers` in Directus. If no processing record is linked in the available snapshot, the panel is hidden rather than claiming processing never occurred; if the snapshot is unavailable, the page reports the uncertainty. Nested cards follow explicit container foreign keys; a record whose parent is not exported as a processing stage shows its recorded parent container without pretending a stage occurred. Recorded status appears as-is, including non-OK values. The MS file badge uses the separate verified-file `data/ms_profile.json`; the processing panel may include MS records without files or with other statuses.

`scripts/build_processing.py` fetches the publicly readable Directus processing collections, reconciles published Field_Data sample IDs and Taxa references against `data/samples.json`, and atomically builds `data/processing.json` containing only validated record IDs, container IDs/labels, parent relationships and recorded statuses. Unlinked and outside-snapshot records are excluded and counted in snapshot metadata; missing containers and conflicting ancestry fail refresh. This static, read-only JSON is loaded only for the Samples list, species pages and sample details; visitors do not query Directus directly. It includes no credentials, protocols, aliquot contents or inferred success. Run `python3 scripts/build_processing.py` after updating `data/samples.json`; a read-only `DIRECTUS_TOKEN` can also be supplied.

## Taxonomy treemap

Open **Treemap** for the full current snapshot, or select a botanical garden/project to show only its field samples. Each rectangle's area is its number of **resolved sample rows**, not species richness. Click a family, then a genus to zoom; use the path buttons to go back. Click an exact identification to inspect its rank, count, and public Catalogue of Life page; **View samples** opens the matching sample list within the chosen garden/project. Family colors stay consistent when changing projects. The high-contrast qualitative palette uses readable text on each color, following [scientific palette guidance](https://www.simplifiedsciencepublishing.com/resources/best-color-palettes-for-scientific-figures-and-data-visualizations); labels and tile areas, not color alone, communicate the Taxa hierarchy. The chart uses the checked-in JSON and native browser HTML/CSS/JavaScript, not Plotly or a second data export.

Only `Field_Data.taxon_ref` and the `Taxa` records' IDs, ranks, names, and `parent_ref` ancestry determine the hierarchy. A species, subspecies, variety, or other linked rank appears under its Taxa family and genus, if present; an identification recorded directly at family or genus rank remains counted at that rank. Resolved Taxa with no family ancestor appear explicitly under **Without a family in Taxa**. Unlinked field observations are excluded but included in the displayed total field-sample count. Every project in the snapshot participates, including projects outside the five named gardens. No new browser-to-Directus permissions or `.env` file are required.

## Species metabolome annotations

Sample and species pages with a Wikidata-linked species offer a lazy [LOTUS Explorer taxon search](https://lotus-initiative.github.io/lotus-explore-rs/search/?taxon=Q161425&execute=true). The link uses the species' mapped Wikidata QID and `execute=true` to run the search on load. A sample identified below species rank uses **its species ancestor in the Directus Taxa parent chain**; genus-level and unresolved records have no species metabolome panel. A species without a mapped QID shows an explicit absence message, not a search for an unrelated taxon. LOTUS displays externally reported chemical occurrences and references from Wikidata/SPARQL, **not** chemicals measured in that field sample or results from Directus `MS_Data`; an empty search does not prove the species has no metabolites. LOTUS does not expose a documented results-only embed, so the iframe shows its complete search interface without cropping, alongside a visible link to open the same search in a new tab if framing or external services fail.

`scripts/build_wikidata_taxa.py` reconciles the sampled species' **exact CoL IDs from Directus Taxa** against [Wikidata's Catalogue of Life ID property P10585](https://www.wikidata.org/wiki/Property:P10585), restricted to Wikidata items ranked species (P105 = Q7432). It makes bounded, rate-limited SPARQL queries **once when you run the exporter** and writes the checked-in `data/wikidata_taxa.json`; it never guesses by scientific name. CoL IDs matched to multiple QIDs are omitted rather than arbitrarily assigned, and request failures leave the last good mapping unchanged. Refresh this mapping after a Directus Taxa refresh when you want newly sampled species to appear:

```sh
python3 scripts/build_wikidata_taxa.py
```

No Directus credential is needed for this step once `data/samples.json` exists. The browser loads the local CoL-to-Wikidata ID mapping on sample and species pages; it does **not** query Wikidata to reconcile CoL IDs. The optional species-photo panel separately reads a mapped item's P3151 from Wikidata as described above. Scrolling to a mapped species' lazy LOTUS iframe sends a visitor's IP address and the species' QID to LOTUS Explorer and its external SPARQL/data services, **not** the Directus sample ID; the iframe and source link suppress the HTTP referrer. The currently deployed GitHub Pages search response does not send frame-blocking headers, but LOTUS's published `_headers` policy specifies `X-Frame-Options: DENY` and `frame-ancestors 'none'` for hosts that honor it. Therefore the external link remains visible even if the iframe is blocked; the rest of the dashboard works when LOTUS or its services are unavailable.

## Directus mass-spectrometry profiling

Each sample page shows a **species-level** badge derived only from Directus: the species in the linked `Taxa` parent lineage is considered to have a recorded MS profile if **any** field sample assigned to that species has a linked `MS_Data` record with status `OK` or `published` and an attached MS file UUID. The badge lists the model and physical ID of each instrument recorded on those MS records, linking to its Directus `Instruments` item. If the currently open field sample has its own linked MS records, those IDs link to `MS_Data` in Directus as well. A green species badge **does not** say the current sample was profiled; the widget distinguishes the two. `OK`/`published` and a file reference are evidence of a recorded MS file, not proof of successful QC, complete downstream analysis, or metabolite identity. **No linked MS file recorded** means none could be joined in this snapshot, not that no experiment took place.

On the field-sample page, the MS badge, species-level instrument summary and **this field sample's** MS record links sit directly below the collapsed Catalogue of Life classification in the identity column, not in the title banner. `#sample/65650` (`dbgi_003141`) has two linked MS files; `#sample/67452` has the same resolved species but no linked MS file of its own, and the panel states that distinction.

`scripts/build_ms_profile.py` fetches public `Field_Data`, `Containers`, `Dried_Samples_Data`, `Extraction_Data`, `Aliquoting_Data`, `MS_Data` and `Instruments` fields (including the instrument-model relation) from Directus. It follows explicit container foreign keys, checks field IDs, sample IDs and Taxa links against `data/samples.json`, and writes a compact, atomic `data/ms_profile.json`. Unlinked or newly created field records outside the published sample snapshot are excluded and counted; conflicting lineage or missing instruments stop refresh. The snapshot contains only MS record IDs, linked field IDs, instrument IDs/model names, statuses, and **safe MS_Data filename basenames** for GNPS; it omits MS file UUIDs, instrument serials and private notes. Refresh after the field/taxonomy snapshot, then serve the site normally. These public collections can be read without moving an `.env` file; only rebuilding `Taxa` requires the existing read-only credential.

## GNPS2 LC-MS dashboards for profiled field samples

On a field sample with linked recorded MS files, the dashboard embeds the [GNPS2 LC-MS viewer](https://dashboard2.gnps2.org/) for that **sample's own** Directus filenames, with a chooser if it has several files. It constructs each USI as `mzspec:MSV000102993:<Directus MS_Data.filename>.mzML`; `MSV000102993` is the common [MassIVE](https://massive.ucsd.edu/) dataset specified for these files, **not** inferred from a filename or from Taxa. Filenames are never used to join records: only `Field_Data → Containers → processing containers → MS_Data` foreign keys establish the sample. A species can have a green MS badge from *other* samples without showing this field sample's GNPS panel. Unsupported or unsafe filenames retain their MS evidence but receive no fabricated GNPS URL. Future datasets need an explicit dataset accession per record or another verified mapping before generating further USIs.

For every selected file GNPS2 starts in **BPI (base-peak intensity)** chromatogram mode through `tic_option=BPI`. The link never carries an invented MS2 scan ID.

The GNPS2 dashboard is embedded automatically for each profiled field sample, with the selected file's **BPI** view. The disclosure can be collapsed to unload the iframe, and the external GNPS2 link remains available. The reported Cloudflare **Error 1033** on the direct GNPS2 URL means its tunnel was unavailable; a Cloudflare HTTP 530 error response also carried `X-Frame-Options: SAMEORIGIN`, which explains Firefox's refusal to display that *error page* in an iframe. It does not establish a permanent GNPS2 framing restriction, and this site cannot restore GNPS2's tunnel. A Directus MS record does **not** guarantee GNPS2 can resolve the file. Loading the embedded viewer or following the link sends the visitor's IP address and the filename—**which may contain the DBGI sample ID**—to GNPS2 and its file services; merely opening a profiled sample page may trigger that request. Link and iframe suppress the page referrer, and no Directus credentials are sent. The provided example `20240307_EB_dbgi_001195_01_01.mzML` was observed in GNPS2 with 4,691 scans, an LC-MS heatmap, and a chromatogram before the tunnel error; other filenames have not been independently checked there.

### LOTUS formula → ChemCalc adduct → GNPS2 XIC

Species pages include an on-demand [ChemCalc](https://www.chemcalc.org/) helper; a **field-sample page shows it only when that sample has a Directus-linked MS file usable in its GNPS2 viewer**. It stays hidden when only another sample of the same species was profiled or when there is no usable MS filename. Copy a **molecular formula** from a LOTUS compound row (a neutral mass alone is not a formula), enter it and the desired ionization (default `H+`), then click **Calculate with ChemCalc**. The embedded calculator shows the resulting ion **m/z**; for example, ChemCalc reports `195.08765` for `C8H10N4O2` with `H+`. This formula is an example, **not** an assertion that this DBGI sample contains that compound. Copy the ion m/z into **Plot XIC in GNPS2** on a **profiled field sample**; the selected sample's own Directus-linked GNPS file opens with `xicmz=<m/z>` and `tic_option=BPI`. Switching that sample's MS files keeps the requested m/z; clearing the input returns to the BPI-only view. An XIC peak is not a confirmed identification; review the GNPS plot, tolerance, MS/MS and controls.

No formula, m/z or calculated result is pulled across third-party iframe boundaries: the visitor copies these two values manually. ChemCalc loads **only after** the calculation is requested, and then receives the formula, adduct and visitor IP, but no sample ID. A direct ChemCalc link remains available if the embedded tool cannot load. GNPS2 receives the m/z along with the selected file USI and visitor IP; the existing file-availability and privacy limitations above still apply.

## Garden progress

**Explore → Garden progress** compares directly linked records for Fribourg, Champex, Neuchâtel, Prague and Kew. The source is **Directus**: `Field_Data`, `Extraction_Data`, `MS_Data` and their linked `Containers` records. Table counts are **cumulative**: **Collected** includes all field records, **Extracted** includes field records with a linked extraction or MS record, and **Profiled** includes field records with a linked MS record. A profiled sample therefore contributes to all three totals. The bar stacks each field sample once, with the profiled segment at the left, then extraction-only, then collection-only; its total width remains proportional to that garden's field-sample count. Segments have slightly rounded outer ends. These indicators describe Directus records, **not verified successful processing**. The current snapshot has no profiled sample lacking a linked extraction record; if a future snapshot does, the chart discloses that its Extracted tally infers that stage from the MS record. No Portal-stage data are used.

`scripts/build_garden_progress.py` reads public Directus fields (or an optional read-only token), reconciles field sample IDs/projects with container identities and explicit dried-sample, extraction, aliquoting and MS relationships, then atomically writes `data/garden_progress.json`. An unlinked processing record is **excluded and counted in the snapshot metadata**, not assigned to a garden; a missing referenced container or conflicting identity stops refresh. Only garden-level totals, source/method metadata, status counts and exclusion counts are published—no sample IDs, filenames, containers or credentials. For a local refresh: `python3 scripts/build_garden_progress.py`.

`data/gardens.json` defines the five garden names, website links and observed Directus project aliases. Fribourg groups `jbuf` and `bg-unifr`, Neuchâtel groups `jbn` and `jbn-new`, and Prague groups `jbp` and `jbp-new`; Champex is `jbc`, Kew is `kew-botanical-gardens`. All counts and taxonomy aggregates are computed from the linked Directus snapshots, **not** copied from the DBGI website or Portal. The five logo cards on the overview open the corresponding **filtered map** by default; an independent link leads to each garden's DBGI website entry. A missing garden catalog does not block the sample list: the page shows raw Directus project filters and identifies the unavailable garden cards.

## Collector leaderboard

Open **Collectors** to rank the Directus `People` records explicitly linked from `Field_Data.collector_ref` by the number of distinct published field samples. Each collector opens with a **Species list** ranked by that collector's sample count: species and infraspecific identifications follow their **Directus Taxa parent hierarchy**, never a field-name match. Names link to the full species page; **View collector samples** shows only that person's field samples of that species. The **Field samples** tab preserves the paginated list of *all* linked field samples, including those not resolved to species, with a dashboard sample link and its original Directus `Field_Data` record.

The leaderboard filters collectors by their recorded name, People ID and available profile IDs, and sorts by count, name or People ID. A collector's Species list filters/sorts all resolved species by scientific name, sample count or Taxa ID; **Field samples** filters/sorts all that collector's field records by ID, sample name, field name, project or date **before paging**, including any selected species scope. These controls do not alter the Species map's recorded coordinates.

**Species map** plots each of that collector's resolved-species field samples with valid recorded GeoJSON coordinates. Intermediate bubbles count samples and split by one zoom level per click; at the maximum zoom each sample is individually clickable, with coincident points displaced visually and linked to their exact recorded coordinates. Popups link to the species and field sample. Records without coordinates or without a Taxa species ancestor stay accessible in the field-sample list; map and species summaries disclose the exclusions. Opening the map loads pinned Leaflet from unpkg and OpenStreetMap tiles, exposing the visitor's IP address and viewed map area to those providers; neither receives a Directus sample ID from the map tile request. The Species list and Field samples tab remain usable if external map resources are unavailable.

The leaderboard is attribution recorded by Directus, not a completeness claim about who was present in the field or about processing outcomes. Records with a collector name but **no `collector_ref` are excluded and counted separately**; free-text spelling is never used to merge people, so two People records with identical display names stay distinct. Cards and collector pages link to that person's **ORCID** and **iNaturalist profile** when their Directus `People.orcid` and `People.inat` fields contain valid identifiers. Mazzarine Laboureau's verified People #25, for example, links to [ORCID 0009-0006-7011-4195](https://orcid.org/0009-0006-7011-4195), [iNaturalist mazzarinel](https://www.inaturalist.org/people/mazzarinel) and the [official DBGI team page](https://www.dbgi.org/team/laboureau-mazzarine/). DBGI team links for other collectors are reviewed **explicit People ID + exact name** matches to the [DBGI network directory](https://www.dbgi.org/network/), not guessed from a name or arbitrary slug. Unmatched or invalid IDs receive no external link. No email, role, research-group data or private notes are exported. Following profile links sends the visitor to those external sites.

Fourteen collectors with a verified DBGI team page and an official avatar show that curator's portrait on cards and detail pages; other collectors use initials rather than an invented picture. The locally hosted 220 × 220 WebP assets in `assets/collectors/` total about 92 KB. `scripts/build_collectors.py` records the reviewed People-ID/name → DBGI page and exact avatar source filename mapping, and only publishes an asset path when that local file exists. The image and attribution are served by this site; loading the portrait does **not** request DBGI's servers. The adjacent DBGI profile link gives its source, and the page credits [DBGI's published website-content CC BY 4.0 notice](https://creativecommons.org/licenses/by/4.0/). Confirm any portrait-specific permissions with DBGI before public deployment if its website-wide notice does not cover a photographer's image.

Run `python3 scripts/build_collectors.py --env-file ../directus-explorer/.env.admin` **after** refreshing `data/samples.json`. The exporter reads `Field_Data` and `People` using a read-only token or local login, including `People.id,full_name,orcid,inat`; it joins source field records to the published sample snapshot by Directus numeric ID **and** sample ID and writes `data/collectors.json` atomically. Public Pages clients load that same-origin snapshot lazily on collectors routes, never call Directus, and reject a collector snapshot built against a different sample snapshot. Collector names and public profile handles are personal information: confirm permission for their public release before deploying.

## iNaturalist curation and identification review

`scripts/build_inaturalist.py` joins the **public Directus `Curation_Data.emi_external_id`** to the published `Field_Data.sample_id` in `data/samples.json`. Run `python3 scripts/build_inaturalist.py` after refreshing samples; it writes `data/inaturalist.json` without credentials (an optional read-only Directus token is supported). The published projection contains linked observations, their Directus observation/community taxon IDs, first-to-last observation photo URLs, their matching `Taxa` CoL usage IDs/names/ranks, and only corroborated photo metadata. No Directus user accounts, private notes or unrelated curation rows are published. The browser loads this optional curation snapshot only on sample-detail and iNaturalist-review pages; overview, sample list, map, and treemap do not download it.

The [iNaturalist identification review](#inaturalist) lists **potential disagreements**, agreements and unassessable records, with search, status filters and local-only checkboxes for selecting observations to inspect; selection does not persist or write to Directus. iNaturalist taxon IDs and CoL IDs cannot be compared numerically. The exporter uses the community taxon ID stored in Directus, looks up its current accepted scientific name/rank via the iNaturalist API, and compares that **name at the same rank** with the resolved CoL Taxa name. No community ID, unavailable API lookup, unresolved CoL name or different ranks is **unassessable**, not a disagreement. Differing names are **review candidates**, not proof of mistaken identification: synonyms and separate taxonomies may disagree. The API is only a lookup; observation identities, photo references and CoL records always come from Directus. Sample pages present the community and resolved names side by side, a compact gallery of all linked photos, and links to the corresponding `Curation_Data` item and original iNaturalist observation. The observer identification is available in a collapsed disclosure. High-resolution photos load from iNaturalist only when displayed, with attribution/license when matching photo metadata exists. Those image requests expose the visitor IP and photo ID to the external host; no images are copied into this repository.

The review table can order the **entire matching observation set before its 200-row display cap** by sample ID, observation ID, community name, CoL name or review status. Its metadata search and status filter combine with the ordering; local review selections persist when a different sort places an observation offscreen.

## Historical weather on sample pages

On opening a sample page with a valid collection timestamp and GeoJSON point, the browser **automatically** requests that record’s hourly weather estimate from the [Open-Meteo historical archive](https://open-meteo.com/en/docs/historical-weather-api). This sends the sample’s coordinates and a three-day date window—not its sample ID—to Open-Meteo; Open-Meteo can also see the visitor’s IP address. The panel displays the recorded local clock **hour’s** estimated 2 m temperature, relative humidity and a WMO weather condition with adapted [Font Awesome Free icons](https://fontawesome.com/license/free) (CC BY 4.0); source, privacy and limitations are in a collapsed disclosure below the compact result. No weather data are bulk-downloaded or stored in the published snapshot. Missing coordinates/timestamps, unavailable historical data, ambiguous daylight-saving hours and network failures show unavailability rather than invented values.

`Field_Data.date` has the form `YYYYMMDDHHMMSS` but no time zone. The panel assumes that recorded clock time is local to the coordinates, matches that hour using the archive’s IANA time zone, and labels this assumption. Open-Meteo provides **gridded model/reanalysis estimates**, not measurements made at the specimen location or confirmation of conditions at the instant of collection. Conditions may come from a weather grid cell kilometres away. Weather data attribution and [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) are linked beside each panel; the adapted Font Awesome Free icon credit is there too. The [free Open-Meteo API terms](https://open-meteo.com/en/terms) allow non-commercial use subject to rate limits; commercial deployment requires an appropriate plan.
